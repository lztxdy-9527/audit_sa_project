## 3. 相对原方案的改进点（A–J，请总架构师逐条裁决）

- **A. 部署方式改为直接落盘**：执行端用工具直接把文件写进磁盘，废除"AI 聊天输出文件内容、人工复制粘贴"方式（后者有截断、转义、编码故障源）。
- **B. 新增 `make_demo_data.py` + `ground_truth.md`**：合成数据时预埋已知异常并留答案册。理由：双脚本交叉校验若无答案册，只能证明"两套实现一致"，不能证明"结果正确"；有答案册才能做召回率/误报率验证。
- **C. 第一天 git init**：用提交历史作为"历史产物不可篡改"的硬证据；每阶段打 tag；`.gitignore` 排除 `.venv/`、`__pycache__/`、日志、数据快照副本。
- **D. 文件名修正**：`methodology_shturl` → `methodology_loop.md`；`harness.md` 建议更名 `AUDIT_CONTRACT.md`（与 Harness 软件同名易混淆；若更名需同步所有提示词，见 Q2）。
- **E. 100w 行只做压测报告**；开发与面试演示用 1k–1w 行，避免演示时长时间等待。
- **F. 编码纪律**写入前置预优化清单：读 CSV 先试 `utf-8-sig` 再探测 GBK（中文财务导出常见），写文件统一 UTF-8。
- **G. 守门点加固**：每次放行前，执行端必须复述"从磁盘读到的当前状态 + 下一步计划"，主理人对照 PROGRESS.md 核验后放行。
- **H. 依赖钉版本**：`requirements.txt` 锁定版本。注意 pandas 3.x / chromadb 1.x 与网上旧教程 API 不同，代码一律按已装版本写。
- **I. "AI 禁止改契约"的技术解释**：这是提示词纪律而非硬锁；真实兜底 = git 提交历史 + 人工守门。面试口径建议：提示词契约 + git 历史 + 人工守门，三层。
- **J. 面试诚实表述**：中心化单控制流 + 角色契约文件，非并行蜂群式多智能体；这恰是禁 Swarm 后能稳定落地的架构。

## 4. 执行端预估总架构师可能提出的质疑及回应

1. **"单会话角色扮演是否撑不起 Agent-Team 叙事？"** → 执行端环境确有 subagent / 工作流多智能体工具，可用真子代理实现 Reviewer；但起步阶段单会话 + 角色契约更稳。是否升级、何时升级由总架构师定（见 Q1）。
2. **"chromadb 默认向量模型首次运行联网下载，面试现场离线怎么办？"** → 阶段 4 前将模型缓存指向项目内目录并预热一次（或换本地 embedding），保证演示离线可用（见 Q5）。
3. **"答案册会不会让『AI 找异常』变成『AI 匹配答案』？"** → 答案册只用于开发期验证脚本正确性；正式演示与压测使用不含答案的新生成数据集。
4. **"100w 行在个人电脑上会不会跑不动/太久？"** → 分块读写 + SQLite 足够；压测报告只需生成一次，演示不用 100w 行。

## 6. 任务交接接口提案（三方协作机制）

- **任务卡**（GPT → 主理人 → 执行端）：字段 = 任务ID / 目标 / 验收标准 / 约束与红线 / 输入文件 / 输出文件 / 是否触及守门点。主理人可直接粘贴到执行端会话，或存为 `audit_sa_project\docs\tasks\TASK-###.md` 让我读取。
- **执行回执**（执行端 → 主理人 → GPT）：每任务产出 `docs\EXEC_REPORT_###.md`：做了什么、产物路径、疑点与偏差、需要谁决策什么。
- **执行端边界**：只落地执行、发现偏差即上报；不自行改架构、不碰契约文件、不到守门点不停。
