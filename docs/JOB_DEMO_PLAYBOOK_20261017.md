# 求职演示与面试说明：采购付款CAAT审计辅助原型

适用版本：2026-10-17四相符演示集成后的合成版本（账证 + 账实一条命令）。实际接受身份与限制以 `data/reviews/task046_dsh_20261017_01/review_result.json` 与 `docs/reviews/REVIEW_TASK_046.md` 为准；TASK-046 已验收。本说明不是审计报告或真实企业项目履历。

## 1. 用什么名字介绍

建议名称：**采购付款审计辅助原型（Python / SQL / SQLite，合成数据）**。

一句话：把模拟ERP导出的采购付款数据，经过质量核验、人工守门、SQL筛查与独立Python复算，变成能追溯到原始Excel的事实底稿，再保存人类初判并只读核验。

30秒介绍可以这样说：

> 我做了一个采购付款审计辅助原型，使用合成Excel里的供应商、应付、付款和分摊四张表。系统先核数据质量和金额勾稽，再通过SQL筛查四类待核查线索，用另一套Python逻辑复算，最后生成能回到原始行和退款记录的事实底稿，并保存人类初判。我重点解决的是计算口径、证据追溯和人工决定与材料绑定；当前演示没有接入大模型，也不自动作出审计结论。

不要把当前版本介绍为已经上线的“自动审计AI系统”“真实企业舞弊识别平台”或“全流程智能审计Agent”。后置AI只是受约束的只读消费扩展方式，没有调用模型。

## 2. 业务逻辑是什么

输入是一个模拟ERP Excel工作簿：suppliers供应商、payables应付单、payments付款/退款主表、allocations付款/退款分摊。付款可分摊到应付单，退款要关联原付款和原分摊；这是一对多关系，不能把主表整笔金额在关联后重复累加。

当前完整模块链是：接收核验 → Gate1 → 标准化/SQLite → Gate2 → SQL筛查 → 独立复算 → 事实底稿 → 人类初判保存 → 只读恢复 → 账证相符（凭证字段级）→ 账实相符（银行流水交易级）。后两段只读消费 canonical 输入 `data/evidence_inputs/task043_v1_1` 与已接受账务，输出四相符摘要（差异不被吞掉，任一步非全匹配演示退出码非 0）。**演示命令从已经接收核验过的固定batch_normal开始**，复核其来源和运行前提；它不是任意新Excel的一键接收向导。

Gate1确认本次接收材料是否可进入标准化；Gate2确认标准化、入库、质量与金额勾稽是否满足筛查前提。结构错误不能靠APPROVE掩盖。演示回放的是已登记合成人类决定，不是在现场冒充真人点击审批。

四条规则的准确含义：

- R01：同一已知应付单、同一收款对象，至少两笔不同原付款的退款后净额各自恰好等于该应付金额，形成重复足额支付线索。分两次合计付清不因此命中。
- R02：按唯一已知应付单汇总，已结算付款分摊减有效退款分摊的净额严格大于应付金额，形成超额线索；不重复乘以付款行数。
- R03：原付款分摊未填写应付关联，或关联ID在所提供台账中不存在。它不等于“没有发票”或“没有真实采购”。
- R04：能找到应付单，但付款收款供应商ID与应付供应商ID按原字符串比较不一致。它是待核查对象差异，不自动等于违规。

只扣截至日内、已结算、有效关联的退款；待结算/失败/作废退款展示但不抵减。R03/R04即使后来全额退款，原有历史关联异常仍保留。金额用整数分，ID不去空格/改大小写/抹前导零；付款主表和分摊金额各自计算，不相加称损失。

## 3. 用本轮实际小样讲一个完整故事

固定主体澄明商贸有限公司，CNY，2026-09-01至2026-09-30，截至2026-09-30。小样是2家供应商、1张应付单、3条付款/退款主表、3条分摊，**不能据此宣称百万行性能**。

应付AP01为5000元；P01付款5000元，P02再付款5000元；R01对第二笔退回1000元。净付款10000−1000=9000元，与应付5000元比较，超额4000元，因此R02命中1条。

R01仍为0：第一笔净额5000元，第二笔退款后净额4000元，只有一笔净额恰好足额，没有两笔都满足R01条件。这说明“重复足额”和“净付款超额”是不同规则，不应期待两者总是一起命中。

现场要说“发现一条4000元超额待核查线索”，不能说“发现4000元损失/舞弊”。是否存在台账范围、业务条件或其他证据问题，必须由人类取证判断。这个合成版本不覆盖预付款、跨期调整或真实ERP的全部场景。

## 4. 实现了什么，有什么价值

实际实现：四表数据质量与关系核验、保留原始来源的标准化、SQLite装载及勾稽、两道材料绑定Gate、四条SQL规则、独立Python复算、可阅读事实底稿、初判输入校验/六快照保存/只读恢复、有界声明历史核验，以及**四相符一条命令演示**（契约校验 + 账证 8/8 + 账实 3/3 + 期间合计，人类结论留空）。运行层19个公开API、17项代码清单、40项Gate1材料属于当前接口与证据契约，不是19个前端页面。

价值首先是审计数据分析的可信处理过程：规则可重复运行；SQL与另一套Python实现对照，减少单一实现错误；应付/付款/退款/分摊和原Excel行可追溯，便于审计人员解释线索；决定绑定当时材料，数据/代码变化不能沿用旧批准；人类判断与未来机器建议分开，减少先看机器意见再补写初判的问题。

这些是当前可展示的技术价值。没有真实企业试点或计时对照，不能写“降低成本80%”“提高审计效率90%”“减少某公司损失”等未测收益。

技术面可讲Python、SQL/CTE、SQLite只读筛查、Excel字段类型/来源映射、整数分、JSON规范指纹与文件SHA区分、Win32独占句柄锁、失败优先与异常链、分阶段测试。哈希只是字节/对象一致性工具，不能证明源业务真实，也不是不可篡改存储。

## 6. 面试常见追问

**和Excel筛选/VLOOKUP有什么区别？** Excel能做其中部分分析；这里把口径、退款关联、质量阻断、两套计算、来源追溯和人工决定绑定成可重复的流程。不要说Excel做不到，也不要把复杂代码量本身当价值。

**为什么SQL后还要Python复算？** 从标准化记录用另一套分组/整数逻辑重算，再与SQL事实逐维比较；不是把SQL结果再求和，也不读取答案册。两者一致降低单一实现风险，仍不证明数据真实或结论正确。

**这算AI项目吗？** 当前运行核心是确定性程序，没有调用大模型。AI用于开发协作应如实说明；业务侧后置AI仅保留只读扩展方式，未实施。更准确地介绍为“为后置AI审计辅助准备受控证据基础的CAAT原型”。

**初判是系统自动给的吗？** API只保存人类明确提供的原文及绑定。演示为自动回放预登记合成夹具，尚无现场真人登录/审批GUI，不能把回放说成人在演示中实际审批。

**为什么初判里写‘通过’，但还有R02线索？** 当前夹具的人类原文包含‘通过/无明显不一致且合规’，程序按授权原样保存，不判断这句话在审计业务上正确。不能把该夹具当作R02已查清的结论；现场以事实线索为主，说明尚需人类核查。需要新的人类判断时应重新明确登记并按版本/事件规则处理，不能改旧记录掩盖矛盾。后置AI尚未实现，所以也没有自动核对判断语义与事实的功能。

**怎么保证金额准确？** 输入先验证精度和类型，转整数分；退款按原分摊先汇总再关联，避免一对多重复计算；主表/分摊分别勾稽；SQL和Python复算精确比较，不用浮点容差凑一致。

**Gate1/Gate2是什么？** 分别对应进入标准化前的接收/范围检查，以及筛查前的装载/勾稽检查。批准绑定当时材料，不能拿旧批准给变化后的材料放行；本地身份是声明，未做强认证。

**程序能代替审计人员吗？** 不能。它提供待核查事实、来源和可复算结果；重要性、取证、缺陷分级、业务合理性与审计结论仍由人类负责。零命中也不能自动等于无问题。

**这个版本有哪些明显限制？** 合成单批次、固定期间/CNY及通用四表；无真实ERP接入、OCR/RAG、网页产品、强认证、AI建议或终判；无大数据规模性能结论。物理junction、并发双进程真实竞态及非合作篡改等未测项仍保留，不能用单机成功推成生产就绪。

**这次测试有发现问题吗？** 有：只读演示的inspect-out可覆盖运行封装，还提前报告zero_write=true。已用自建场景真实复现并保全/恢复原件，随后定点修复为只向允许证据域独占创建新JSON，并在实际写出后再次核保护文件。正常/负例与完整演示重新回归。这是输出路径保护问题，不是已发现金额算法算错。

**你本人做了什么，代码是否AI写的？** 按真实分工回答，可以说明采用AI辅助开发、任务卡与独立复验；只把自己实际完成、能解释和能修改的部分写进简历。不要把模型代写隐藏成完全手工开发，更不要虚构企业客户/团队规模/上线指标。面试前至少能自己解释四条规则、退款口径、两道Gate、独立复算和这次bug。

**为什么历史证据很多，能不能只留成功的？** 失败/修正现场用于说明结果如何产生、哪些限制仍存在；不能为作品整洁删掉失败证据。展示时用导航和少量当前产物，不需要把全部历史当演示界面。已知139项历史损失仍登记，不能声称历史证据全部完整。

**下一步做什么？** 先在另行授权下设计后置AI只读建议与人类终判、再考虑适配真实数据和认证/部署；这些是规划，不写成已完成。当前保留接口不代表未来永远不需要适配或可保证零返工。
