### 3.1 被纠正的原句（接入方案 P1 旧稿）

该概括已删除；修正后 P1 明确两类值**计算对象不同、字段含义不同、不互相替代**：

> **指纹口径（澄清，纠正过度概括）**：本方案区分两类 64 位小写十六进制值……**文件 SHA-256**：取自**确切原始字节**——包括工作簿、数据库、Markdown/契约文件以及 JSON 文件；同一对象若以不同排版/换行保存为两个 JSON 文件，其文件 SHA 也可能不同。**规范 JSON 对象指纹**：仅取自**约定的 canonical JSON 字节**（如既有已验收体系中的 `packet_sha256`、`record_sha256`）。因此不得把"批内所有指纹"一律说成以 canonical JSON 计算，也不得用对象指纹替代文件字节哈希（或反之）。

### 3.2 输入保真（P1 新增澄清）

> **输入保真口径（澄清）**：P1 的入口是**内存中的提交对象**，它能按原文保存**人类字符串字段与接收到的对象快照**；但确定性序列化**不等于**保存了原始 JSON 文件的排版/换行/BOM 字节，因此**不能承诺"JSON 不重排"式的原始文件保真**。若后续设计**文件输入**并要求原始提交保真，则须**另存该次确切文件字节/文件 SHA**，并与解析对象的规范指纹**分别绑定**。本轮只澄清候选接口边界：**不选定、不设计、不实施**新的 I/O 接口，也不修改任何现有实现。
