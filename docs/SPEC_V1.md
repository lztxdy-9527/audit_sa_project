# 采购付款异常筛查与审计辅助：V1 业务规格

版本：V1 / TASK-001；日期：2026-10-11；状态：待总架构师验收的实施规格。

本文件落实主理人批准的 TASK-001。现有原方案及执行端环境报告仅作为历史背景，其中处罚记录、权限日志、默认 RAG 和百万行压测不属于本版。本文是后续生成器、标准化程序、SQL、独立复核及底稿共同遵守的业务口径，尚不代表程序已经实现。

所有案例均为合成数据。规则输出是待核实线索，不能直接认定舞弊、损失、控制缺陷或审计调整，也不能代替审计人员的职业判断。

## 1. 业务范围与实务对应

模拟企业为“澄明商贸有限公司”，检查 2026 年 9 月办公耗材采购付款，截至日为 2026-09-30（包含当日）。本版只处理单一公司、人民币、无期初余额的完整模拟业务历史。演示中应付单、付款及退款业务日期均在 2026-09-01 至 2026-09-30；范围外日期应报告范围不符，不能静默过滤。

本版支持一次付清、分期付款、一笔付款对应多张应付单、部分付款尚未匹配应付单，以及全额或部分退款关联原付款。本版不支持预付款、外币、红字应付单、现金折扣、手续费及跨期调整。发现范围外业务须列出来源记录和原因，停止受影响流程，不能自动换算或套用规则。输入提供者须确认范围和导出条件；仅靠这四张表不能证明实际企业的全部业务已被提供。

实务中拟请求 ERP 导出的结构化明细；第一版使用通用模拟 Excel 工作簿。供应商主数据说明付款对象，应付单说明账面应付款项，付款记录说明模拟资金事件，关联明细说明资金分配到哪些应付单。应付单不是发票，不能把应付单编号或缺失关联解释成税务发票情况。

合同、发票、验收单、银行回单及授权代收材料属于后续人工核实证据，不属于本版自动识别输入；不做 OCR，不连接真实 ERP，不宣称兼容真实金蝶或用友模板。模拟 `SETTLED` 和银行流水号是案例设定，不是取得真实银行证据的声明。真实接入时必须另行核实状态来源和导出字段，不能把“付款单已审核”等同于银行已支付。

数据准备阶段统一称为“审计数据接收、核验与标准化”。数据已经规范时，核验通过即可；不为展示清洗能力制造无意义错误，不把真实业务疑点清洗掉。

## 2. 输入工作簿与四表数据字典

### 2.1 共同约定

- 输入为 `.xlsx` 工作簿，必需工作表为 `suppliers`、`payables`、`payments`、`allocations`，每表第一行为下述英文列名，后续为明细。缺列、重名列、重复或缺失的必需工作表属于结构问题；额外工作表或列先登记，不自动纳入规则，Gate 1 须明确接收范围。
- 下述所有字段列均必需存在；“允许空”仅指某条记录的单元格可空。完全空白行单独计数并保留原行号映射，不算业务明细；部分字段缺失的行不能当空白行跳过。
- ID、单据编号、银行流水号以文本提供并按字符串读取，保留前导零，禁止用数值或行号替代业务 ID。数值单元格形式的标识不能凭显示格式猜补前导零，须报告输入问题。必填文本不能只有空白；标识中的字符不自动改写或模糊匹配。
- 主键在对应工作表内唯一。`ap_number` 只是展示字段，不承担关联键或唯一键职责。名称相同不代表主体相同，不能按名称自动合并 ID。
- 日期为有效日期，标准表示为 `YYYY-MM-DD`；Excel 原生日期单元格可以无损转换为该表示。含歧义的日期文本、无效日期和额外时间成分须报告，不猜测日期顺序。
- 金额单位为人民币元，严格正数，最多两位小数。可以接收明确的十进制数值或文本，如 `5000.00`；禁止公式单元格、货币符号混入值、千分位文本、科学计数文本及无法解析的值。禁止自动四舍五入修复超出两位的小数；格式不符须报告。
- 程序标准金额为整数分，使用十进制解析后精确转换。例如 `5000.00` 对应 `500000` 分，不用二进制浮点数累计或设浮点误差容限。Excel 数值的读取方式仍须在后续代码任务验证，不把本任务视为 Excel 读取测试。
- `currency` 必须为 `CNY`。非人民币明确报告超出范围。空单元格和空字符串表示空值；不得把文字 `NULL`、`N/A` 或 `0` 自动当作空标识。
- 保留工作簿原始字节及单元格原值、原类型、工作表名、Excel 行号和列名。来源记录定位由工作簿 SHA-256、工作表名与原始 Excel 行号组成；路径和业务 ID 只能作为附加信息。不得覆盖原文件。

### 2.2 `suppliers`：供应商及收款对象主数据

每行代表一个本次模拟范围内的供应商或收款对象。

- `supplier_id`：文本，必填，主键。其他表通过此 ID 关联。
- `supplier_name`：文本，必填，主体显示名称。授权代收对象可以在此表中单独登记，但本表不证明其收款授权成立。

### 2.3 `payables`：有效应付单

每行代表一张本次范围内有效应付单，不是发票行或商品行；本表不混入作废单、预付款、红字单。

- `ap_id`：文本，必填，主键，也是关联明细的应付键。
- `ap_number`：文本，必填，单据展示编号，允许不同单据有相同展示编号。
- `supplier_id`：文本，必填，必须存在于 `suppliers`。
- `ap_date`：日期，必填，本版范围内的应付业务日期。
- `payable_amount`：金额，必填，整张有效应付单本次应支付的正数金额。不是商品明细金额，也不是尚未支付余额。
- `currency`：枚举文本，必填，仅 `CNY`。

无期初余额且无本版排除事项时，应付金额是 R01、R02 的比较基准。不能把每条付款关联中的应付金额反复相加。

### 2.4 `payments`：付款／退款资金事件

每行代表一笔资金事件；本版模拟一条主表记录对应一笔银行收付。真实 ERP 一张单据对应多笔银行流水时不能直接套用此粒度，需要另行设计适配。

- `payment_id`：文本，必填，主键；付款和退款共用本列的唯一编号空间。
- `transaction_type`：枚举文本，必填，`PAY`（对外付款）或 `REFUND`（收回原付款）。
- `original_payment_id`：文本；`PAY` 必须为空，`REFUND` 必填并指向原 `PAY` 主表记录。
- `payee_supplier_id`：文本，必填，必须存在于 `suppliers`。对 `PAY` 表示实际收款对象；对 `REFUND` 表示退回款项的原收款对象，不是本企业。
- `payment_date`：日期，必填。`PAY` 为付款业务日期，`REFUND` 为款项退回日期，均在本版范围内。
- `amount`：金额，必填，整笔资金事件的正数金额。退款也填正数，通过类型确定资金方向。
- `currency`：枚举文本，必填，仅 `CNY`。
- `settlement_status`：枚举文本，必填，`SETTLED`、`PENDING`、`FAILED` 或 `VOIDED`。
- `bank_reference`：文本；`SETTLED` 必填且在全表已结算事件中唯一，其他状态允许空。本版只有一个公司和一个银行流水标识命名空间。真实多账户流水号是否全局唯一须在未来适配时确认。

仅 `SETTLED` 计入资金计算。其他状态仍保留并按状态列示记录数及名义金额，不能当作真实收付款。不同主表 ID 但相同已结算银行流水标识是数据质量冲突；不同流水标识的两笔付款可能是真实重复付款，不能为了“去重”删除。

### 2.5 `allocations`：资金事件与应付单关联明细

每行代表一笔资金事件分配到一个应付对象的金额，不是额外的一笔资金收付。

- `allocation_id`：文本，必填，主键。
- `payment_id`：文本，必填，必须存在于 `payments`，决定本行付款／退款类型、状态、资金对象与日期。
- `ap_id`：文本，允许空。非空值可以在所提供 `payables` 中不存在；这两种情况都必须保留，以便 R03 分析，不作为强制外键错误删除。
- `allocated_amount`：金额，必填，本次分摊的正数金额。
- `original_allocation_id`：文本；付款分摊必须为空，退款分摊必填并指向原付款的分摊明细。

每笔主表事件至少有一条分摊，分摊金额合计须精确等于该事件 `amount`。一笔事件对同一 `ap_id` 只能有一条标准明细；空 `ap_id` 作为同一“未指定对象”检查唯一性。未知但非空的不同标识各自保留。源表出现重复组合时报告冲突，不在未审定来源含义时自动汇总。

部分未匹配付款也须完整分配：例如付款 5000.00，可有已知应付分摊 3000.00 和 `ap_id` 为空的分摊 2000.00，不能只保留已知部分。

## 3. 关联、退款与数据质量处理

### 3.1 必须成立的关系

`payables.supplier_id`、`payments.payee_supplier_id` 必须存在于主数据。`allocations.payment_id` 必须存在于主表。以上关系缺失导致无法确定主体或资金事件，属于阻断问题。

`allocations.ap_id` 为空或不在台账中是特意允许的业务线索状态，须进入已接受数据和总体勾稽。应付供应商与付款收款对象不同同样不是结构错误；保留两侧记录供 R04 比较。

本版不允许同一事件对同一应付对象出现重复分摊，防止来源粒度不明；后续真实 ERP 明细可能需要专门的汇总适配，但本版不能假装已经完成。

### 3.2 有效退款

退款主表必须关联一个存在且已结算的 `PAY`，对象和币种与原付款一致，退款日期不早于原付款日期。退款明细必须关联原付款明细，该原明细的 `payment_id` 必须等于退款主表的 `original_payment_id`。

退款明细的 `ap_id` 必须与原明细完全一致，包括同时为空或同时为同一个未知标识；不得用退款重新指定应付对象。每一原付款明细对应的截至日累计已结算退款分摊，不得超过原分摊金额。每笔退款也须满足主表金额与分摊合计一致，因此整笔累计已结算退款同样不能超过原付款。

`PENDING/FAILED/VOIDED` 的退款保留但不扣减付款。不得用一笔未结算退款消除已结算超付。类型或关联错误、退款超额及日期逆序是阻断问题，不能把错误退款计算成正常的负净付款。

### 3.3 数据质量与范围问题的分流

- 接收阶段可识别的结构问题（缺表、缺列、重名列、无法读取）须记录来源与问题，Gate 1 不放行。
- 主键重复、无效标识类型、关键金额／日期无法解析、资金事件外键缺失、主数据外键缺失、已结算流水号冲突、分摊不平、非法退款，以及范围外业务须隔离记录并列明原因；Gate 2 不放行。若 Gate 1 前已发现阻断问题，不能先假装通过再等待 Gate 2。
- 隔离是保留问题记录和诊断信息，不是静默删除。第一版不在关键问题未解决时对残余子集出具完整筛查结果，也不把缺失金额补零。不因人类点击批准而免除程序阻断条件。
- 修复应由输入提供者更正新副本，启动新批次并保留旧批次；不得改写原始快照。无法解析金额的批次只能给出已知小计、未知金额记录数等受限信息，不能宣称全表金额勾稽通过。
- 无应付关联、超过应付金额、收款对象不同等可计算的业务现象是待核实线索。不得因为它们会触发规则而阻止正确数据入库或自行修正交易。

## 4. 金额计算与勾稽口径

以下变量单位均为整数分，金额相等使用精确相等，不使用误差容限。

对原付款分摊 `a`：

```text
paid(a) = 原 PAY 事件为截至日已结算时的 allocated_amount，否则为 0
refunded(a) = 指向 a 的截至日已结算有效 REFUND 分摊金额之和
net(a) = paid(a) - refunded(a)
```

对可找到的应付单 `b`：

```text
paid_total(b) = 所有 ap_id=b 的已结算 PAY 分摊之和
refund_total(b) = 所有 ap_id=b 的已结算有效 REFUND 分摊之和
net_total(b) = paid_total(b) - refund_total(b)
overpayment(b) = max(net_total(b) - payable_amount(b), 0)
```

应付维度跨不同收款对象汇总，用于 R02；付款对象差异由 R04 单独列示，不能默默把该分摊移给其他应付单。

接收、标准化和入库必须记录四表各自的来源业务行数、接受行数、隔离行数及空白行数。对应每表应满足“来源业务行数 = 接受行数 + 隔离行数”；Gate 2 放行时关键隔离问题须为零。每张表各自对账，不能把四表行数相加称为资金交易数。

必须完成以下金额勾稽：

1. 每笔主表金额等于其分摊金额之和，包括非结算事件和未匹配部分。
2. 主表已结算 `PAY` 总额等于已结算付款分摊总额；已结算 `REFUND` 总额等于已结算退款分摊总额。
3. 主表净资金额等于已知应付关联净额加缺失应付关联净额。后者包含空标识和台账不存在标识，不可漏算。
4. 标准化前的可解析原始金额、标准化金额和入库金额按表及字段分别勾稽，并按付款／退款和状态分组。问题金额无法解析时不出完整通过结论。

主表和分摊表是两种观察粒度，不能把两者相加。应付总额按唯一 `ap_id` 汇总，不要求其等于付款总额；未付款、超付款等本来就可能使两者不相等。

## 5. 四条规则的确定性定义

### R01：现存重复足额付款

只对已知应付单分析。按 `(ap_id, payee_supplier_id)` 分组，找出截至日已经结算的不同原付款，其中每笔对该应付单的 `net(a)` 精确等于该应付金额。满足条件的不同 `payment_id` 至少为 2 时输出一条线索，列出全部满足条件的付款、对应流水、关联明细和退款。

这里判断的是退款后的现存重复足额状态，不是所有历史重复付款。分期付款 2000.00 + 3000.00 不满足；一笔付款分摊至两张应付单也不是两笔资金事件。不同主表记录的已结算流水重复须先阻断，不能借此制造 R01。

### R02：应付单净付款超额

按唯一 `ap_id` 汇总截至日已结算付款和有效退款分摊。当 `net_total(b) > payable_amount(b)` 输出一条线索，显示应付金额、付款总额、退款总额、净付款及超额金额。严格大于才命中；不自行推导重要性阈值，也不自动形成会计调整。

同一应付单可能同时命中 R01、R02。R02 超额只能按唯一应付单汇总一次，不能乘以付款行数或其他命中数。

### R03：在提供的应付台账中未找到关联对象

逐条检查已结算 `PAY` 的分摊。`ap_id` 为空或在所提供 `payables` 中不存在时，每条分摊输出一条线索，并区分“未填写关联”和“填写的标识不在台账”。不得改写为“无发票”“无真实采购”或“违法支付”。

该明细不参加 R01、R02；也不能因无法找到应付供应商而强行判 R04，但其金额保留在总体勾稽。记录原付款额、已退回额、当前净额；即使全部退款，原先发生的缺失关联事实仍保留。

### R04：收款对象与应付供应商不同

逐条检查能找到应付单的已结算 `PAY` 分摊。如果主表 `payee_supplier_id` 与应付单 `supplier_id` 不同，每条分摊输出一条线索。按 ID 比较，不能只比较名称或改写主体。

线索提示“需核实是否为授权代收、主体映射问题或付款错误”，并列出合同、代收授权及银行回单等待补证据。不得仅凭对象差异判定违规。退款后仍保留已经发生的对象差异事实，并展示退回额和当前净额。

### 5.1 命中标识、证据与展示

R01 的命中键由规则、应付 ID、收款对象 ID 组成；R02 由规则与应付 ID 组成；R03、R04 由规则与原付款分摊 ID 组成。后续实现须采用无歧义的结构化组合，不能无转义拼接可冲突的字符串。

每条线索至少能追溯到相关应付、主表付款、关联明细、退款、银行标识和原始来源记录。R03 没有应付记录时明示缺失，不能伪造来源。展示金额必须注明是整笔资金、分摊、退款、净额还是超额，不能把缺失关联的分摊额当作整笔付款额。

不汇总四条规则的涉及金额作为损失。总体资金、涉及的唯一付款事件以及唯一应付单的超额金额分别呈现。人类初步判断前只展示确定性事实、计算过程和待核实问题，不展示 AI 预填判断、候选等级或结论。

## 6. 十四组手工验收案例

### 6.0 记录简写与共同默认值

以下为文档内的手工案例，不是已生成的 Excel 数据，也不是后续千行数据集异常数量。各组使用独立数据集，相同 ID 可以在不同组重复。每组默认 `suppliers` 包含 `S001=甲供应商`、`S002=乙收款对象`。均为合成主体。

为避免重复完整行，记录采用以下固定简写。省略字段仅按本节默认值展开，不能由实施者猜测：

```text
AP(ap_id, supplier_id, payable_amount)
  -> ap_number=ap_id, ap_date=2026-09-05, currency=CNY
PAY(payment_id, payee_supplier_id, amount, bank_reference, status=SETTLED)
  -> transaction_type=PAY, original_payment_id=空,
     payment_date=2026-09-10, currency=CNY, settlement_status=status
REF(refund_id, original_payment_id, payee_supplier_id, amount, bank_reference, status=SETTLED)
  -> payment_id=refund_id, transaction_type=REFUND,
     payment_date=2026-09-20, currency=CNY, settlement_status=status
A(allocation_id, payment_id, ap_id, allocated_amount, original_allocation_id=空)
  -> allocations 对应各列；“空”表示真实空值，不是字面文本
```

每组输入除了明确列出的记录和两条默认主数据外，没有其他业务记录。所有简写金额单位为人民币元。预期命中只针对该组；有阻断问题时预期是停止筛查，不是“零异常”。

### C01 一次足额付款

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S001,5000.00,B001)
A(A01,P01,AP01,5000.00)
```

预期：R01—R04 均不命中；主表付款及分摊各为 5000.00，净额 5000.00。理由：只有一笔足额付款，关联和主体一致，无超额。

### C02 分期付款

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S001,2000.00,B001)
PAY(P02,S001,3000.00,B002)
A(A01,P01,AP01,2000.00)
A(A02,P02,AP01,3000.00)
```

预期：四条规则均不命中；净额 5000.00。理由：两笔分期合计足额，任一笔均不等于整张应付金额，不能因为有两次付款就判重复。

### C03 合并付款

输入：

```text
AP(AP01,S001,6000.00)
AP(AP02,S001,4000.00)
PAY(P01,S001,10000.00,B001)
A(A01,P01,AP01,6000.00)
A(A02,P01,AP02,4000.00)
```

预期：四条规则均不命中；只有一笔资金事件，主表付款总额 10000.00，分摊合计 10000.00。理由：两个关联行不能让整笔付款金额重复累计成 20000.00。

### C04 两笔现存重复足额付款

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S001,5000.00,B001)
PAY(P02,S001,5000.00,B002)
A(A01,P01,AP01,5000.00)
A(A02,P02,AP01,5000.00)
```

预期：R01 一条（AP01、S001），R02 一条（AP01）；付款及净额 10000.00，超额 5000.00；R03、R04 不命中。理由：确有两笔不同流水，各自净额均为 5000.00。两条命中不能相加成损失。

### C05 非重复足额的超付款

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S001,3000.00,B001)
PAY(P02,S001,2500.00,B002)
A(A01,P01,AP01,3000.00)
A(A02,P02,AP01,2500.00)
```

预期：仅 R02 一条，净额 5500.00，超额 500.00。理由：合计超额，但没有两笔各自足额的付款。

### C06 重复付款后的退款

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S001,5000.00,B001)
PAY(P02,S001,5000.00,B002)
REF(R01,P02,S001,5000.00,BR001)
A(A01,P01,AP01,5000.00)
A(A02,P02,AP01,5000.00)
A(AR01,R01,AP01,5000.00,A02)
```

预期：四条规则均不命中；付款 10000.00、退款 5000.00、净额 5000.00。理由：P02 分摊净额为零，不能继续认定现存重复足额或净超额；原付款和退款均保留。

变体 C06b：把 R01 和 AR01 金额同时改为 1000.00。预期仅 R02 一条，净额 9000.00、超额 4000.00；P02 净额为 4000.00，所以不满足 R01 的“两笔净额各自足额”。

### C07 未填写应付关联及部分未匹配

输入：

```text
PAY(P01,S001,5000.00,B001)
A(A01,P01,空,5000.00)
```

预期：R03 一条（A01）；总体净资金额 5000.00，缺失关联净额 5000.00。理由：记录有效保留，只有关联信息缺失；不执行 R01、R02、R04。

变体 C07b 的完整输入：

```text
AP(AP01,S001,3000.00)
PAY(P01,S001,5000.00,B001)
A(A01,P01,AP01,3000.00)
A(A02,P01,空,2000.00)
```

预期：仅 R03 一条（A02）；总付款 5000.00 = 已知关联净额 3000.00 + 缺失关联净额 2000.00，R03 涉及分摊额为 2000.00，不能误写成整笔 5000.00。

### C08 应付标识不在所提供台账

输入：

```text
PAY(P01,S001,5000.00,B001)
A(A01,P01,AP_MISSING,5000.00)
```

预期：仅 R03 一条（A01）；总净资金及缺失关联净额均为 5000.00。理由：标识 AP_MISSING 不在台账，缺失关联不是可删除的无效资金事件；不得外键删除，不得宣称企业没有发票。

### C09 收款对象不同及退款后保留事实

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S002,5000.00,B001)
A(A01,P01,AP01,5000.00)
```

预期：仅 R04 一条（A01），同时列明 S001 与 S002。净额 5000.00，不超额。理由：实际收款对象与应付供应商不同，但还需要人工核实代收授权、主体映射及回单，不能自动判错。

变体 C09b：增加 `REF(R01,P01,S002,5000.00,BR001)` 及 `A(AR01,R01,AP01,5000.00,A01)`。预期仍为 R04 一条，付款 5000.00、退款 5000.00、净额零；历史收款对象差异不会因退款消失。

### C10 非结算状态

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S001,5000.00,空,PENDING)
PAY(P02,S001,5000.00,空,FAILED)
PAY(P03,S001,5000.00,空,VOIDED)
A(A01,P01,AP01,5000.00)
A(A02,P02,AP01,5000.00)
A(A03,P03,AP01,5000.00)
```

预期：四条规则均不命中；各状态保留一条，名义金额各 5000.00；已结算付款和净资金均为零。理由：表里有记录不代表资金已经支付。

变体 C10b：在 C04 输入上增加 `REF(R01,P02,S001,5000.00,空,PENDING)` 和 `A(AR01,R01,AP01,5000.00,A02)`。预期仍有 R01、R02 各一条，净额 10000.00、超额 5000.00；待结算退款不能抵减。

### C11 同一银行流水重复导入

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S001,5000.00,B001)
PAY(P02,S001,5000.00,B001)
A(A01,P01,AP01,5000.00)
A(A02,P02,AP01,5000.00)
```

预期：已结算流水标识冲突，Gate 2 不放行，不发布 R01—R04 筛查结果。理由：尚不能认定有两笔真实银行付款，不能自动删一条，也不能报告现存重复足额付款。

### C12 主表与分摊不平

输入：

```text
AP(AP01,S001,6000.00)
AP(AP02,S001,4000.00)
PAY(P01,S001,10000.00,B001)
A(A01,P01,AP01,6000.00)
A(A02,P01,AP02,3000.00)
```

预期：主表 10000.00 与分摊 9000.00 相差 1000.00，Gate 2 不放行。理由：不能悄悄补一条未知分摊或只分析 9000.00 后宣称完整。

### C13 超额退款

输入：

```text
AP(AP01,S001,5000.00)
PAY(P01,S001,5000.00,B001)
REF(R01,P01,S001,6000.00,BR001)
A(A01,P01,AP01,5000.00)
A(AR01,R01,AP01,6000.00,A01)
```

预期：退款分摊超过原付款分摊 1000.00，Gate 2 不放行。理由：不能把它算成正常的负净付款并继续筛查。

### C14 结构、主键与解析失败的独立变体

以下每个变体都独立从 C01 的完整输入开始，仅执行所述变更：

- C14a：从 `payables` 表头删除 `payable_amount` 列。预期接收结构检查失败，Gate 1 不放行，不能填默认金额。
- C14b：在 `payments` 中再复制一条完全相同的 P01 记录。预期主键重复，最迟在 Gate 2 前阻断，不能自动去重或当作两笔付款。
- C14c：把 P01 的 `amount` 改为文本 `N/A`。预期关键金额无法解析，隔离并阻断；不能补零，不能宣称全量金额勾稽通过。
- C14d：把 P01 的 `payment_date` 改为 `2026-09-31`。预期无效日期，隔离并阻断；不能滚动修正为十月日期。
- C14e：把 P01 和 A01 的金额同时改为 `5000.001`。预期超过两位小数，阻断，不能舍入到 5000.00 通过。

以上是输入质量问题，不是业务异常命中；隔离后不得对其余行出具本批次完整筛查结果。

## 7. 人机顺序、验收与后续接口

业务流程为：接收快照与核验 → Gate 1 人工确认 → 标准化、入库与勾稽 → Gate 2 人工确认 → 四规则及程序性自查 → 复核 → 保存人类独立初步判断 → AI 对照建议 → 人类最终判断。

人类可以写“暂不能判断，需要补充证据”，并说明原因。人类初步判断保存前，系统和执行 AI 都不得提前生成候选等级、候选结论或预填判断。初步判断保存后，AI 才能按事实和已有判断提出对照意见及取证建议；证据不足时必须指出不足，不补造结论。重要性和最终判断由人类决定；本模拟规则不设置自动重要性阈值。

后续接口最少需要保存：输入来源及导出范围、快照哈希、代码／规则／配置版本、批次状态、两处人工放行记录、数据质量清单、数量金额勾稽、规则线索及来源映射、复核记录、人类初步判断、后置 AI 建议及最终人工判断。此处只是行为规格，本任务不创建运行目录、数据库、配置文件或 CLI。

后续代码验收须验证本文件十四组案例及各变体。生成器和独立答案册是下一任务；检测程序不得读取答案册来产生线索，两套程序一致也不能替代已知案例验证。本任务完成的是文档和手工预期，不宣称 SQL、Excel 读写、守门点或端到端流程已通过测试。
