## 3. 四项修复规格

### A. 运行失败返回 2，尽可能留下真实失败现场

接收器的读取、复制、哈希、日志创建、材料渲染／写入等运行错误，需要由入口统一处理。可以拆小函数，但不要把异常吞掉后返回成功，也不能把运行错误归为质量阻断。

- 建批次前的参数拒绝继续退出 2，不创建批次；输入读取失败等运行问题也退出 2。
- 已创建批次后发生错误，不删除现场、不自动换目录重跑、不覆盖既有批次。
- 批次根目录仍能写入时，保存 FAILED_RUNTIME 清单，记录失败阶段、错误、已有文件的真实存在状态、已知哈希及实际 checker 调用情况。未得到的值为 null，未启动 checker 不虚构命令退出码或质量报告。
- 尽可能写出明确的“核验未完成”材料及错误日志；保留部分快照、已产生的报告等，不能把不完整文件说成完整快照。
- 如果连清单／材料都无法写入，仍退出 2，并在 stderr 告知失败、无法保存的文件和已创建的现场路径。无需假装存储故障下所有文件都能保存。
- 只有要求的材料都已成功生成，且输入／快照／代码／报告检查完成，才能最终宣布 DEV_GATE1_PACKET_READY 或 BLOCKED_QUALITY。发生材料生成失败时，不得遗留 DEV_GATE1_PACKET_READY 清单。

可以在本次新建批次的同一次运行内维护失败状态、完成状态或临时文件；这不授权重开、改写历史批次。不要仅在最外层打印 traceback 后退出，不留可保存的失败清单。

### B. 校验报告结构，缺失信息不得补成零问题

接收器只做所消费报告的结构／类型和一致性核验，继续复用真实 checker，不复制其业务校验逻辑。

- JSON 顶层必须是对象；workbook、checker 等要能取到要求的哈希字段。
- structure、row_accounting、issues、issue_counts_by_code、amount_summary、reconciliation 等被材料消费的字段必须存在且类型正确。需要遍历的内部容器及条目，也应按现有 checker 的实际格式验证。
- 缺少必需区段、顶层／嵌套类型错误、JSON 语法错误、缺失报告、报告哈希不符、退出码与 result 矛盾，均为 FAILED_RUNTIME／退出 2。
- 不可用报告保留原文件和真实存在状态、可获取的文件哈希、错误原因；不要修补、重存或伪造质量报告。
- 结构无效的报告不能继续传给正常材料渲染逻辑。材料明确“核验未完成”，未知数量、问题数、金额不补零，不出现“未记录数据质量问题”的成功表述。
- 金额中的合法 null 必须继续接受；质量阻断报告可能包含缺表、缺列及有限数量／金额，不能因业务质量有问题而把结构正确的报告错误归为运行失败。

不要额外要求质量报告证明企业主体、历史完整性或正式批准。不要引入新依赖或重新计算审计规则。

### C. 验证两份源码留档与实际执行版本相等

不能只记录 code_snapshot 文件的哈希：接收器和 checker 的两个留档副本，均须与本次对应源码哈希一致；执行期间源码本身也须稳定。副本缺失、不可读取或不相等，均退出 2、状态 FAILED_RUNTIME。

在清单中记录可追踪的比较结果。继续用原 checker CLI 对本批次输入快照核验，不能改成调用答案册或旧报告。

本项是留档一致性检查；不扩展成签名服务、权限隔离或抵御同权限恶意篡改的安全能力。

### D. 原样保存来源声明

`--source-description` 用 strip 或等效方法判断是否全为空白，但清单的 source_description 必须等于传入的原字符串。非空字符串中的首尾空格、换行等不自动修改。

候审 Markdown 如需转义以正常展示可以处理展示文本；清单仍存原声明。来源描述仍是未验证声明，不是批准或真实性证明。
