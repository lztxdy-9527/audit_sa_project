## 4. 核心 API、只读和成功条件

提供固定公共接口：

    screen_sqlite(database_path, load_report: dict, *, cutoff_date="2026-09-30") -> dict

核心只消费数据库及其匹配的装载报告，不接收答案册、场景标签或期望命中数。不得导入生成器或从答案册／旧筛查结果产生事实。SQL 不硬编码案例 ID、金额或种子。

明确区分 RuleScreenBlocked（前提／范围不成立）与 RuleScreenError（文件／SQL／核对／来源读取等运行失败）；都不返回成功报告，错误给出字段或阶段、相关路径及原始原因。

必须落实：

- 路径解析后仅接受 data/sqlite_tests 内已存在的最终数据库文件；拒绝目录、缺失文件、越界和 `.staging`。缺失数据库不能被 sqlite3 自动创建。
- load_report 必须是本层所消费结构可用的对象，batch_status=DEV_SQLITE_VERIFIED、mode=DEVELOPMENT_TEST_ONLY、next_step_allowed 为实际 False，装载／schema 版本为本卡冻结版本。报告记录的数据库路径须与实际输入一致，实际字节哈希须与 database_sha256 相等。
- 从数据库实际读取 run_metadata，核对开发态标识、装载／schema 版本、输入哈希及对象指纹与装载报告相等；冻结装载器／schema 哈希与当前冻结文件相符。不能只信报告里的“成功”字符串。
- 用 SQLite URI 的 mode=ro 打开，再启用并实测 PRAGMA query_only=ON；不使用普通可创建连接作为回退。查询只用固定 SELECT／CTE，不建临时表或视图，不执行 DDL／DML／executescript，不更新元数据。
- 日期范围仍为 2026-09-01 至 2026-09-30，包含截至日。本次 cutoff_date 只支持 2026-09-30；其他值明确阻断。范围不符须报告，不以 WHERE 静默过滤后出完整结果。计算时仍明确使用截至日条件。
- 金额只用整数分和精确比较，不用浮点累计或 TOTAL()；汇总溢出明确失败，不改用浮点容差。无退款行的合计可为 0，缺失金额／结构不可补零。
- 从数据库独立计算本次总体已结算 PAY／REFUND 及已知／缺失关联净额，对照装载报告的相应口径，保留主表净额=已知+缺失的勾稽；金额或来源缺项／不一致即失败。
- 正常关闭必须成功，关闭出错不返回成功；已有错误后的清理不能掩盖原错误。查询前后数据库字节哈希须相等，记录实际核验；这用于证明未改输入，不宣称防恶意篡改。
- 只有前提、规则、证据读取、核对、关闭和只读保护都成功，才返回 batch_status=DEV_RULES_COMPUTED、mode=DEVELOPMENT_TEST_ONLY、next_step_allowed=false。核心不保存输出文件；测试调用方保存本次新报告。

## 5. SQL 计算粒度：先汇总退款，再关联原付款

为每条截至日已结算原 PAY 分摊形成计算基础：原付款分摊额、指向它的截至日已结算 REFUND 分摊合计、两者之差。退款按 original_allocation_id 汇总后再关联原分摊，避免多条退款令原付款金额被重复 SUM。

退款的合法关系由冻结上游保证；原付款和退款主表都须按 transaction_type／settlement_status／日期选取。PENDING／FAILED／VOIDED 的退款不能抵减。真实无退款对应 0，不是丢弃退款明细。

四条规则按 SPEC 实现：

- **R01**：仅已知应付，按 ap_id＋payee_supplier_id 分组。在本组中，每笔原付款对此应付的分摊净额等于应付金额；满足条件的不同 payment_id 至少两个，输出一条分组线索，列出全部满足条件的付款。三笔足额也是一条组线索，不输出两两组合。这里金额是该组符合条件付款的合计，不冒充应付的全部净付款。
- **R02**：仅已知应付，按唯一 ap_id 汇总已结算原付款及退款分摊，跨收款对象计算；净付款严格大于应付金额才命中。输出应付、付款、退款、净付款和超额；一个应付一条，不乘以付款或其他规则行数，不设置重要性阈值。
- **R03**：逐条检查已结算原 PAY 分摊，空 ap_id 或台账查不到各输出一条，区分 EMPTY_AP_ID／AP_NOT_IN_LEDGER。保留原分摊、已退回、当前净额；全额退款后仍命中历史缺失关联事实。未知应付不能参加 R01／R02，也不能强判 R04，资金仍在总体勾稽中。
- **R04**：逐条检查能找到应付的已结算原 PAY 分摊，实际 payee_supplier_id 与应付 supplier_id 按原字符串精确比较。不同则一条；全额退款后仍保留历史对象差异。展示双方 ID，固定提示需核实授权代收、主体映射或付款错误，不自动判违规。

R03／R04 的基础不能加“净额大于 0”过滤。不要把 REFUND 自身再当一笔原付款生成 R03／R04。付款主表整笔金额与分摊金额分开命名和展示。

所有业务参数绑定，包括用于读取证据的含引号 ID 和截至日。表列名只来自固定代码／SQL 白名单，不拼接数据中的指令。

## 6. 输出契约和证据

成功报告至少包含：规则实现／SQL 版本与文件哈希、截至日、数据库路径与前后哈希、装载来源标识、模式／停止标记、总体勾稽、规则命中数、findings 数组、统计口径及限制。

每条 finding 至少包含 rule_id、结构化 hit_key、明确单位的 amounts_cents、related_ids、source_rows／来源证据和固定事实描述。沿用答案册已有的结构化键形状便于单独验证：

- R01：`{rule_id, ap_id, payee_supplier_id}`。
- R02：`{rule_id, ap_id}`。
- R03／R04：`{rule_id, allocation_id}`。

禁止把键无转义拼成 `ap_id + "|" + payee_supplier_id`。输出稳定排序，按规则和原字符串键排序，不依赖数据库行序、集合或随机数。每个结构化命中键恰好出现一次。

amounts_cents 可采用与答案册相同的名称，但必须在说明中明确：R01 的 payable_amount／net_per_payment／组内 net_total，R02 的 payable_amount／paid_total／refund_total／net_total／overpayment，R03／R04 的 allocated_amount／refunded_amount／net_amount。值均为整数分；整笔 payment amount 单列，不用它替代分摊金额。

证据至少包含相关应付、原付款、原分摊、退款主表和退款分摊的 ID、实际业务值和来源定位；从 source_records 读取 workbook_sha256／sheet／excel_row／完整 cells，JSON 解码后保留。若展示主体名称，其主数据来源也应可追溯。

列出相关退款时说明其状态、分摊及是否计入；非结算退款可以作为关联记录展示，但不扣减。R03 没有应付记录时明确缺失，不能伪造应付或来源。来源缺项／非法 JSON 不得默默省略后返回“证据完整”。

总体资金单独从 payments 粒度计算，不在一对多关联后 SUM 整笔金额。分别展示涉及的唯一原付款事件集合／数量及其整笔已结算总额、R02 按唯一应付汇总的超额金额；注明前者是整笔付款总额，不能当作缺失关联分摊额或损失。四规则涉及金额不相加称为损失，R01／R02 同时命中也不得重复累计 R02 超额。

不增加 AI 判断字段、严重等级、自动审计结论或人类判断预填值。固定事实描述和 SPEC 已要求的待核实提示可以输出。
